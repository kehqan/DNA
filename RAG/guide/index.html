Implementation Guide

What each external project actually is, how it works under the hood, whether you install it or merely read it — and then the ordered path from an empty folder to a system running in shadow mode.

Read this first

The architecture document says what to build. This one says how to proceed and, more importantly, why each step exists. It exists because a reference list is not the same as understanding: knowing that CVE-KGRAG contributed "taxonomy anchoring" tells you nothing about what that repository actually does, whether you are meant to clone it, or what you would do with it if you did.

So Part I decodes every external source in plain language — what problem it solves, how it works mechanically, and a blunt verdict on your relationship to it. Part II is the build path: ten steps, each with its purpose stated before its instructions, because a step you perform without understanding its purpose is a step you will perform badly.

The single most important thing on this page

You are not adopting any of these projects wholesale. Four of the six are reference material — things to read, learn a pattern from, and close. Only two involve installing anything, and one of those is optional. If you finish this guide and your dependency list has six new entries, something has gone wrong.

Because the hard part of this system is not retrieval — it is having a rulebook worth retrieving from. Every project above solves retrieval. 02

The sources, decoded

6 projects
LightRAG
HKUDS (University of Hong Kong Data Science lab) · open-source Python framework
Optional install
https://github.com/HKUDS/LightRAG
What problem it solves

Ordinary RAG chops documents into chunks, embeds them, and retrieves the chunks most similar to your question. That works until the answer depends on a relationship spread across several chunks — "which rules modify this rule" is exactly that kind of question, and similarity search cannot see it. LightRAG's answer is to build a knowledge graph alongside the vector index and search both.

How it actually works, step by step
  1. You hand it documents. It chunks them using one of several strategies.
  2. An LLM reads each chunk and extracts entities and relationships — "X is a type of Y", "A causes B". These become graph nodes and edges. This is the step that costs money and time, and the step whose output you cannot fully control.
  3. It also embeds the chunks into a vector index, as normal RAG would.
  4. At query time it searches both layers — entity-level detail plus graph-level themes — and merges the results. This dual search is its central claim.
  5. New documents merge into the existing graph without rebuilding everything, which matters if your corpus changes constantly.
What we take from it
  • The dual-layer idea itself — graph and vectors together, not one or the other. Our λ blend is a version of this with an explicit, tunable knob instead of an internal heuristic.
  • Its model-role split. LightRAG configures separate models for extraction, querying, keywording and vision, on the reasoning that a cheap fast model suffices for mechanical tagging while the final answer needs your best one. We copy this directly as CLASSIFY / RETRIEVE_ASSIST / REVIEW.
  • Incremental updates as a design requirement, not a nice-to-have.
  • Its own warning that the Python SDK is intended for embedded and research use, and production integrations should go through the REST API server. Worth heeding if you use it at all.
What we deliberately do not take

Its automatic graph construction — the headline feature. An LLM inferring "these two rules seem related" is not good enough when the relationship carries legal weight. We need an edge that means precisely "R-410 waives the second-source requirement in R-042 under a stated condition", authored by an editor who is accountable for it. An inferred edge cannot carry that meaning, and a confidently wrong inferred edge is worse than no edge.

So do you install it?

Only if, at Step 6, you would rather run its retrieval server than write roughly two hundred lines of retrieval code yourself. If you do, you feed it your rules and use it purely as a search engine while ignoring its graph builder. Many teams will find writing their own simpler, because the retrieval logic here is not complicated — it is a filter, a similarity lookup, a PageRank call, a weighted sum, and a neighbour expansion.

RAG-Anything → and what you actually want, MinerU
RAG-Anything: HKUDS · MinerU: OpenDataLab
MinerU: install
https://github.com/HKUDS/RAG-Anything
https://github.com/opendatalab/MinerU
What problem it solves

Standard RAG assumes your documents are text. Real institutional documents are PDFs containing tables, figures, multi-column layouts and scanned pages — and naive text extraction turns a clean table into unreadable soup. RAG-Anything wraps a document parser so that tables, images and equations survive ingestion as structured objects rather than mangled strings.

How it actually works
  1. Parsing. MinerU (or Docling, or PaddleOCR) reads the PDF and emits typed content blocks — this is a heading, this is a paragraph, this is a table with rows and columns — while preserving reading order and layout hierarchy.
  2. Understanding. Each block type goes to a dedicated handler: a vision model for images, a structured interpreter for tables, a LaTeX-aware parser for equations.
  3. Graph construction. Every element becomes an entity, cross-modal relationships are inferred, and a "belongs to" chain preserves the document's section hierarchy.
  4. Retrieval. Hybrid vector plus graph search, weighted by which modality the query seems to care about.

Only stage 1 matters to us. Stages 2–4 solve a problem we do not have: we are not answering questions about the PDF, we are converting it into a rulebook once and then never reading the PDF again.

What we take from it

The parsing stage, which in practice means installing MinerU directly rather than the wrapper around it. You point it at Editorial_Standards_v3.pdf and it hands back structured markdown with the tables intact and the section hierarchy preserved. That output is the input to your migration script.

One thing to know before you start

RAG-Anything has been merged into LightRAG — multimodal parsing is now a built-in feature of the latter rather than a separate package. So it is not really a fork in the road any more. Check the current state of both repositories before installing either; this consolidation is recent and the packaging may have moved again.

CVE-KGRAG
Yuning-J · cybersecurity threat-intelligence knowledge graph
Concept only — never install
https://github.com/Yuning-J/CVE-KGRAG
What it is

A working production system that ingests the US National Vulnerability Database — around 190,000 catalogued software vulnerabilities — and turns them into a searchable knowledge graph used by a downstream cyberdefence simulation. It is not a demo. It is the most operationally serious project in our reference set.

Why a security tool is the closest analogue to a newsroom rulebook

Because the shape of the data is nearly identical, once you strip the subject matter away:

CVE-KGRAGOur system
A CVE — one catalogued vulnerabilityA rule — one catalogued standard
CWE / CAPEC — fixed external classification schemes every CVE maps ontoOur taxonomy — fixed categories every rule maps onto
CVSS score — standardised severityblocking / warning / advisory
Affected product and vendorApplicable desk and language
Relationships between vulnerabilities and attack patternsrelated_rules and qualified_by edges
The one idea we take — taxonomy anchoring

CWE and CAPEC are externally standardised catalogues. When CVE-KGRAG classifies a vulnerability, it picks from a fixed list somebody else maintains — it cannot invent a new weakness category because it felt like it. That constraint is the reason 190,000 entries stay coherent instead of degenerating into thousands of near-duplicate labels.

We have no external standards body for editorial rules, so we write our own catalogue and then treat it as if it were external — frozen, versioned, editable only by a small group, and enforced mechanically in CI. Every extraction prompt is told the list and forbidden from extending it.

A second, quieter lesson

It runs on NetworkX — an in-process Python graph library, not a graph database — at 190,000 nodes and millions of relationships. That is a useful calibration: if NetworkX handles that, your few hundred rules do not justify standing up Neo4j on day one. It also runs local models rather than cloud APIs, which is worth remembering if source-protection concerns ever rule out sending draft text to an external provider.

kg-rag
Vector Institute · research comparison of retrieval strategies
Method only — never install
https://github.com/VectorInstitute/kg-rag
What makes it different from everything else here

Every other project asserts that its approach works. This one was built to find out which approach works. It implements three competing graph-RAG retrieval strategies over the same data and benchmarks them against each other with a proper evaluation harness and hyperparameter search.

The three strategies, and what each teaches us
  • Entity-based with beam search — match query terms to graph entities by embedding, then walk outward through their neighbourhood. This is closest to what we are building, and its presence in a serious benchmark is mild reassurance that the approach is sound.
  • LLM-generated Cypher — let the model write a database query and run it. Attractive: it handles open-ended questions no fixed pipeline anticipated. Dangerous for us: a subtly wrong query returns fewer rules and looks like a clean result. Silent under-retrieval is the worst possible failure in a compliance tool.
  • GraphRAG-style community detection — cluster the graph and summarise each cluster. Strong for "what is our general posture on X", weak for "which specific rule applies to this sentence". Wrong shape for our problem, and expensive.
What we take — the posture, not the code

Do not assume the hybrid architecture beats plain vector search. Prove it. Our five eval arms exist entirely because of this project: arm A is naive RAG as the honest baseline, and arms B through E each add exactly one component so you can see what that component bought you. If arm A scores within noise of arm E, the graph is decoration and should be removed.

That is an uncomfortable test to design, which is exactly why it is worth designing.

"How to Query a Knowledge Graph with LLMs Using gRAG"
Cristian Leo · Towards Data Science · tutorial article
Concept only
https://medium.com/data-science/how-to-query-a-knowledge-graph-with-llms-using-grag-38bfac47a322
The problem it demonstrates

Pure similarity search has a specific, recurring failure: it ranks by wording resemblance, so an item that is genuinely central to the topic can be outranked by one that merely shares vocabulary. The article shows a concrete case where an item with lower similarity ends up ranked higher once graph structure is taken into account — and that single worked example is the clearest argument for the whole hybrid approach.

Its mechanism, in plain terms

It computes two scores for every candidate and blends them:

score = λ · semantic_similarity  +  (1 − λ) · graph_relevance
  • Semantic similarity — cosine distance between embeddings. How much does this sound like the query?
  • Graph relevance — a Personalized PageRank score. Start a random walk from nodes related to the query and see how often it lands here. How structurally central is this, relative to what was asked?
  • λ — the dial. At 1.0 you have ordinary vector search. At 0.0 you ignore wording entirely. In between you choose how much each signal counts.
How we extend it

The article treats λ as one global constant. We make it per category, stored in the taxonomy, because the right trade-off differs by stakes: a legal rule must surface even when the draft phrases the problem in unfamiliar words (low λ, favour recall), while a style rule about one specific term should fire only when that term is genuinely in play (high λ, favour precision). Turning one number into five is a small change with a large effect on how the system behaves.

Do not copy its code

The author states plainly that the implementation is a basic version with real limitations, and recommends a proper PageRank-based approach or an established framework for production use. Take him at his word: read it for the reasoning, then implement the idea with networkx.pagerank(), which supports the personalization vector this needs.

pdichone/knowledge-graph-rag
Course material · Neo4j + LangChain worked examples
Skim or skip
https://github.com/pdichone/knowledge-graph-rag
Honest assessment

A teaching repository with several small modules — basic graph creation, a worked RAG example, a healthcare implementation, some text-prep tooling. There is no novel framework here and nothing to depend on. Its one genuine use: if nobody on your team has built a knowledge graph before, the healthcare module shows a compliance-shaped domain modelled as a graph end to end, which makes the abstract concrete in about twenty minutes. Read it once for orientation, then close it. If your team is already comfortable with graphs, skip it entirely — it will not tell you anything the other sources do not.

03

The build path

10 steps

Each step below states its purpose first, because the purpose determines whether you have done it correctly. A step performed to the letter but against its purpose is worse than a step skipped — it produces something that looks finished and is not.

STEP 1Inventory before anything else3–5 days
Purpose: to find out how big the problem actually is before committing to a shape for it. Almost every failed knowledge-base project began by designing a schema for a corpus nobody had counted.
What you do
  • List every document that contains a rule — style guides, standards manuals, legal memos, wiki pages, that PDF a departed editor wrote in 2017.
  • For each: rough page count, last updated, who owns it, whether anyone actually follows it.
  • Estimate discrete rules per document. A rough count is fine; an order of magnitude is what matters.
  • Flag contradictions between documents. There will be some. Do not resolve them yet — just record them.
Done looks like

A single spreadsheet with every source document, an estimated total rule count, and a named owner per document. You can answer "roughly how many rules are we talking about?" with a number rather than a shrug.

The trap

Starting to write YAML during this step because it feels more productive than counting. Resist. Every hour spent here saves several later, and a schema designed against an imagined corpus will not survive contact with the real one.

Sources usedNone — this is entirely yours
STEP 2The taxonomy workshop1–2 weeks
Purpose: to agree a fixed vocabulary that everything else is built on. This is the highest-leverage step in the project and the one most likely to be rushed, because it involves meetings rather than code.
What you do
  • Get standards editors in a room. Not engineers deciding what editors probably mean.
  • Extract the taxonomy that already exists implicitly — editors already group rules in their heads. Find those groupings rather than inventing new ones.
  • Settle five things: categories, subcategories, desks, languages, severity tiers.
  • Define severity operationally: what does "blocking" permit and forbid, concretely, in the CMS?
  • Decide who may change the taxonomy later, and make that list short.
Done looks like

taxonomy.yaml exists, is committed, and has been read and approved by someone senior enough to defend it. Every category has a one-line definition that distinguishes it from its neighbours.

The trap

Too many categories. If you have fifteen, you have a filing system, not a taxonomy — and classification becomes ambiguous, which defeats the point. Five to seven is the working range. When a rule seems to need a sixteenth category, it usually needs a subcategory instead.

Sources usedCVE-KGRAG — the anchoring principle
STEP 3Schema plus twenty-five hand-written rules2 weeks
Purpose: to discover what the schema is missing while the cost of finding out is still twenty-five files rather than four hundred. This step is a deliberate, small-scale failure test.
What you do
  • Write the rule schema as JSON Schema.
  • Pick your two or three most explicit categories — usually sourcing and legal, because they are written down precisely and argued about least.
  • Hand-write twenty-five real rules. By hand. No LLM assistance at this stage.
  • Deliberately include rules with exceptions and cross-references — those are what stress the schema.
  • Write validate.py and wire it into CI so a bad rule cannot be merged.
Done looks like

Twenty-five rules pass validation, and you went at least one full week without needing to add a field. If you are still adding fields, the schema has not stabilised and Step 4 will be built on sand.

The trap

Automating this step. The whole value is in the friction: hand-writing rules is how you discover that your exceptions field cannot express "unless the subject is a public figure, in which case rule R-088 applies instead". An LLM would have quietly flattened that into prose and you would not have noticed until much later.

Sources usedNone — hand-written by design
STEP 4Build the graph from the YAML3–5 days
Purpose: to turn authored files into a queryable structure — and to establish, permanently, that the graph is derived. Nobody edits it. It is regenerated on every build and is therefore always exactly what the rules say.
What you do
  • pip install networkx. That is the entire infrastructure requirement.
  • Write build_graph.py: read the YAML, create a node per rule and per taxonomy value, create edges from the reference fields.
  • Skip anything not status: active — drafts must never reach the index.
  • Compute base PageRank with severity as the personalization vector, and cache it.
  • Add build/ to .gitignore. This is not housekeeping — it is what enforces the derived-not-authored rule.
Done looks like

Delete build/ entirely, run one command, and get an identical graph back. If that is not true, something is being hand-maintained and will drift.

The trap

Reaching for Neo4j because a graph "should" live in a graph database. At this scale it is a database to operate, back up and secure in exchange for nothing you need. CVE-KGRAG runs vastly more data on NetworkX. Escalate when you have a query you genuinely cannot express, not before.

Sources usedCVE-KGRAG — NetworkX at scalegRAG article — PageRank
STEP 5Ship the mechanical engine — no LLM yet1 week
Purpose: to put something genuinely useful in front of editors before any model is involved. This is the first point at which the project stops being a plan and starts being a tool — and it earns the credibility that the harder half will need.
What you do
  • Compile every type: mechanical rule into patterns and structural checks.
  • Implement quote-span detection so unless_in: direct_quote works — banned-term rules almost always exempt direct quotation.
  • Run it over a hundred recent published articles and read every hit yourself.
  • Fix or reclassify anything producing noise. A mechanical rule that misfires is a bug, not a judgement call.
Done looks like

Near-zero false positives across a hundred real articles, and an editor who has seen the output says it would have caught something real. No LLM has been called at any point.

If the project stops here, it was still worth doing

A validated rulebook plus deterministic checking is a real, shippable product. Everything after this point adds capability but also adds risk — and this is the last step where the system cannot possibly be confidently wrong.

Sources usedNone — plain Python by design
STEP 6Retrieval — the λ decision point1–2 weeks
Purpose: to select which rules the LLM will see. This is where retrieval quality is decided; the model can only reason about what you hand it, and everything it never sees is invisible to the system.
What you do
  • Decide: build or borrow. Write ~200 lines yourself, or run LightRAG's REST server as a search engine. Both defensible.
  • Embed each rule's statement, rationale, hints and — most importantly — its bad example, which is the text closest in register to an actual violation.
  • Filter by taxonomy metadata first: desk, language, status. Cheap and exact, before any scoring.
  • Score with the λ blend, reading λ from each rule's own category.
  • Then expand the subgraph. Pull in every rule connected by QUALIFIED_BY, EXCEPTS or RELATED_TO, regardless of score.
Done looks like

Given a test sentence you can print the retrieved set and explain every entry — this one by similarity, that one by PageRank, this third one purely because an edge pointed at it.

The trap

Skipping expansion because scoring "already works". It does work — for finding the rule. It cannot find the exception to that rule, because an exception's wording resembles the article even less than the rule's does. Expansion is the entire justification for having built a graph; without it you have an expensive vector store.

Sources usedgRAG article — λ blendLightRAG — dual-layer, optional server
STEP 7The LLM review layer1–2 weeks
Purpose: to apply judgement to what retrieval selected. Note how late this arrives — six steps in. That ordering is the point: by now the model is a component inside a structure, not the structure itself.
What you do
  • Split model roles: cheap model to classify desk and language, strongest model to review.
  • Constrain the prompt hard — only the supplied rules, cite rule IDs exactly, quote spans verbatim, never escalate severity.
  • Require explicit exception handling: if a supplied qualifier applies, report suppressed_by rather than flagging.
  • Validate every returned rule_id against the real rule set and discard anything that does not exist.
  • Apply confidence floors by severity — lower for blocking, higher for advisory.
Done looks like

It runs end to end on a real draft and every flag cites a rule ID that exists. Hallucinated IDs are caught and dropped by code, not trusted because the model sounded certain.

The trap

Letting the model decide severity. Severity belongs to the rule, is set by editors, and is not a judgement the model is authorised to make. If a model can promote an advisory to blocking, editorial authority has quietly moved from the standards desk to a prompt.

Sources usedLightRAG — model-role split
STEP 8Evaluation — try to disprove your own design2 weeks
Purpose: to establish whether any of the complexity you have just built is earning its keep. Every step so far assumed the hybrid approach is better. This step tests that assumption honestly, with the possibility of a negative answer.
What you do
  • Assemble 30–60 real drafts with violations annotated by standards editors.
  • Include all four required case types — clean articles, obvious violations, violations phrased unlike the rule, and violations where an exception legitimately applies.
  • Run arms A through E. Arm A is naive vector RAG, the honest baseline.
  • Sweep λ per category and write the winners back into taxonomy.yaml.
  • Report intervals, not point estimates. Thirty articles is a small sample and should be described as one.
Done looks like

Blocking-rule recall at or above 0.95 at acceptable precision, and you can state what each component contributed by comparing adjacent arms.

Be prepared for the uncomfortable result

If arm A scores within noise of arm E, the graph and the λ machinery are decoration and should be removed. That would be a genuinely good outcome — a simpler system that performs identically is strictly better. The purpose of this step is to make that finding possible, which is precisely what most projects avoid.

Sources usedVectorInstitute/kg-rag — the entire method
STEP 9Migrate the remaining rulesongoing
Purpose: to convert the rest of the corpus now that the schema has been validated by real use and the eval harness can detect when a migrated batch is bad.
What you do
  • Install MinerU. Run it on each legacy PDF to get structured markdown with tables intact.
  • Feed sections to an LLM with the vocabulary-constrained migration prompt.
  • Everything emerges as status: draft. No exceptions, no shortcuts.
  • A named editor reviews each rule and promotes it to active.
  • Verify type classification by hand on every rule marked mechanical — a judgement rule mislabelled mechanical produces confident nonsense.
  • Re-run the eval after each batch. A migration that degrades recall is a migration to roll back.
Done looks like

Every rule is active with a named owner and a page reference back to its source document. Nothing was promoted automatically.

The trap

Bulk-promoting drafts to clear a backlog. The review gate is the only thing standing between a machine-extracted approximation of a rule and a rule the newsroom is actually held to. Once it is bypassed, provenance is fiction.

Sources usedMinerU — PDF parsingRAG-Anything — the pipeline pattern
STEP 10Shadow mode, then gated rollout3+ weeks
Purpose: to learn what the system does on live traffic before it can interfere with anyone's work. Offline evaluation on curated cases always flatters a system; real drafts do not.
What you do
  • Run the full pipeline on real drafts and log everything, show nothing.
  • Have standards editors review the shadow log weekly and mark each flag correct or incorrect.
  • Measure real precision and recall on live traffic, not curated cases.
  • Then enable for one pilot desk — blocking and warning only, advisory suppressed until precision is proven.
  • Log every override with user, rule, timestamp and written reason. That log is both audit trail and future eval data.
  • Word the interface carefully: "no flagged issues", never "approved".
Done looks like

Two to four weeks of shadow data, a precision figure you would defend in a newsroom meeting, and one desk using it voluntarily.

The trap

Skipping shadow mode because the eval numbers looked good. Shadow mode is the cheapest possible way to discover that a rule was mis-classified as blocking — and the alternative is discovering it when the tool stops a real story from publishing on a deadline.

04

Decisions you will actually face

Build retrieval or run LightRAG?

Build it if the retrieval logic reads as straightforward to your team — a filter, a similarity lookup, a PageRank call, a weighted sum, a neighbour expansion. Roughly two hundred lines, fully under your control, no version drift.

Run LightRAG if you would rather not maintain that, want its storage backends and incremental indexing, and are comfortable pinning a fast-moving dependency. Use its REST server, not the embedded SDK — its own documentation recommends this.

NetworkX, Postgres or Neo4j?

NetworkX until you have a concrete reason to move. Postgres if the CMS needs to query rules in the same transaction as everything else. Neo4j only when editors want ad-hoc graph exploration or qualification chains get genuinely deep. Escalating early costs operational overhead and buys nothing measurable.

How many rules before the graph earns itself?

The graph pays off in proportion to cross-references, not rule count. Two hundred independent rules need no graph. Fifty rules with twenty exception relationships need one badly. Count your qualified_by edges after Step 3 — if there are almost none, question whether the graph belongs in v1 at all.

When is a rule mechanical?

Only when it can be checked by exact pattern matching with no interpretation whatsoever. "Never use term X outside direct quotes" is mechanical. "Avoid loaded language" is not, however much you wish it were. When uncertain, classify as judgement — an over-cautious classification costs an LLM call, while an over-confident one produces a deterministic wrong answer nobody thinks to question.

06

Questions worth answering early

Why not just put the whole rulebook in the prompt?

For a few hundred rules with a long-context model, you genuinely could — and for a first prototype it is a reasonable shortcut worth testing as a baseline. It stops working when the rulebook grows, when cost per check matters at newsroom volume, and when you need to know which rules were considered for a given flag. Retrieval is what makes the system auditable, not just what makes it cheap.

Why YAML rather than a database table?

Because rules have nested structure — exceptions with conditions and required sign-offs, multiple examples, lists of cross-references — that a flat row flattens badly. And because git gives you review, blame, rollback and diffing for free, which is exactly the tooling a disputed rule change needs. A database can come later as a read model; the authored source should stay in files.

Who maintains this after launch?

Answer this before Step 2, not after Step 10. The system's accuracy is a direct function of whether someone owns the rulebook. The owner and last_reviewed fields exist to make ownership explicit and staleness visible — but they only work if a real person is accountable for acting on the staleness report.

What if editors disagree with a flag?

That is the system working. Every flag cites a rule ID with a source document and page, so the disagreement becomes a concrete argument about a specific written rule rather than about the tool. Sometimes the rule is wrong and should change; sometimes the classification is wrong. Both outcomes improve the rulebook, which is why dismiss-with-reason is logged rather than silently discarded.

Could this be built with an off-the-shelf RAG product instead?

Partly. Any competent RAG product will retrieve relevant rules and produce plausible commentary. What none of them will do is enforce a fixed taxonomy, guarantee that a rule arrives with its exceptions attached, keep mechanical checks away from the model entirely, or make every flag traceable to a reviewed, owned, versioned rule. If those four properties do not matter for your use case, buy something. If they do — and in a newsroom they do — they are the system, and retrieval is the easy part.
